Install dependencies
```
docker run --rm -v $(pwd):/app -w /app composer:2.2 composer install
```

Example script:
```
docker run --rm -v $(pwd):/app -w /app composer:2.2 php example/run.php
```

PHPStan:
```
docker run --rm -v $(pwd):/app -w /app composer:2.2 php vendor/bin/phpstan analyse --level 10 ./src
```

Tests:
```
docker run --rm -v $(pwd):/app -w /app composer:2.2 vendor/bin/phpunit
```

# Design Reasoning

## Загальний підхід
- Сервіс спроєктований простим і компактним, у стилі, звичному для Laravel/CakePHP-проєктів малого/середнього розміру.
- Зовнішній код працює лише з фасадом `DocumentValidator`. Усе внутрішнє – правила, конфігурації, репозиторій – приховано в неймспейсі сервісу.
- `DocumentValidatorInterface` існує для мокування сервісу в тестах, а не для багатьох реалізацій.
- Multi-tenancy свідомо зведена до мінімуму: виходимо з shared DB з колонкою `tenant_id` у таблицях; сервіс викликається в контексті авторизованого користувача з явною передачею `tenant_id`.

## Rules
- Конфігурація правил завантажується з БД, на її основі створюється інстанс правила. Розглядав два варіанти передачі параметрів: правило приймає масив і саме перевіряє наявність потрібних ключів – або конструктор з типізованими аргументами. Зупинився на другому – явно, легко читається, зручно тестувати. Розпакування масиву в аргументи конструктора робить callable під час реєстрації правила; окрема фабрика на кожне правило здавалася зайвою.
- Розглядав два варіанти додавання нових правил: «хардкод»-мапінг `name => class` у фабриці – або реєстрація через callable. Зупинився на другому: якщо правилу знадобиться специфічна залежність, всередині callable її можна отримати з DI-контейнера. У реальному проєкті така реєстрація жила б у service provider. `RuleFactory` при цьому залишається максимально простою і зручною для тестування. Мінус: ім'я, що вказується під час реєстрації, у реальному проєкті знадобилося б і на UI – там довелося б продумувати додаткові нюанси.
- В `RuleInterface` думав передавати дані для валідації не аргументами `$content` і `$metadata`, а іммутабельним класом: з появою нових полів для валідації не довелося б правити сигнатури низки класів. Зупинився на простішому варіанті – для поточного набору полів цього достатньо.
- Розглядав інтерфейс правила з парою методів `isValid()` + `getErrors()` – багатьом це звично, але залежність від послідовності викликів виглядає погано. Зупинився на одному методі `validate()`, що повертає помилки.
- Конфігурацію правил тенанта отримуємо з репозиторію, працюємо з ним через інтерфейс – це знадобиться в тестах. Якби з'явився UI – у фасаді сервісу були б методи керування налаштуваннями, що зберігають конфігурацію в БД через цей самий репозиторій.

## Validation result
- Правила повертають `ValidationError` напряму – той самий тип, що віддає `ValidationResult`. Проміжний per-rule результат з мапінгом розглядав, але вирішив не плодити шари.
- Виходив з того, що документ без правил – валідний; утім, це вже питання бізнес-логіки.
- Локалізацію повідомлень про помилки свідомо опустив.
- Префікс Validation у `ValidationResult` і `ValidationError` – імена навмисно однозначні та «довгі», щоб під час імпорту в інших частинах системи не виникало колізій та аліасів.

## Exceptions
- Усі ексепшени сервісу реалізують `DocumentValidatorExceptionInterface` – так їх легко перехопити разом. Ім'я довге з тієї ж причини, що й у `ValidationResult`.
